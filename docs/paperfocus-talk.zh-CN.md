# PaperFocus 演示讲稿

**建议时长：5—7 分钟**

## 开场

大家好，今天我想介绍一个我刚做的小工具，叫 **PaperFocus**。

不过在演示之前，我先用一句话介绍它背后的模型。

这个工具使用的是 TypeSafe AI 的 **Jev**。Jev 属于一种叫作 **System One** 的模型。它不负责写长篇回答，而是专门负责快速判断、分类和打分。TypeSafe 官方文档称，多数请求可以在大约 100 毫秒内完成；同一份内容还可以同时判断多个问题。

> 演示提示：这里展示 PaperFocus 首页，然后直接拖入准备好的论文。

## 功能演示

大家现在看到的是 PaperFocus。

我先上传一篇 PDF 论文。上传完成之后，我可以直接用自然语言提问。比如：

> 这篇论文的实验是如何设计的？

发送之后，Jev 会判断论文中的每个候选段落、每个句子与这个问题到底有多相关。

系统不会重新生成一篇总结，而是直接回到原论文，把最相关的句子高亮出来。黄色越明显，代表它在这一次分析中越重要。

如果问题涉及某张 Figure，系统还会把图片和图注作为同一处证据，用虚线框标出图片，并保留图注的文字高亮。

右侧会列出所有相关位置。点击任何一条，都可以直接跳转到论文中的原始位置。我还可以调整最低显著度，只保留最重要的几处，也可以按照原文顺序或者相关程度排列。

我还可以继续问：

> 这篇论文的核心贡献是什么？

或者：

> 作者使用了哪些数据集？

> 论文存在哪些局限？

它的作用不是替我读完论文，而是根据我的问题，快速告诉我：**这篇论文最值得我亲自阅读的位置在哪里。**

## 为什么做这个工具

我做这个工具的原因，其实来自一个很具体的阅读问题。

读过论文的人应该都知道，有些论文可以先看摘要，但真正重要的论文还是要自己精读。因为模型生成的一段总结，往往会压缩很多实验条件、限定范围和细节。

但完全靠自己从第一页慢慢读到最后一页，又会比较慢。

另一种方法，是把论文交给 GPT 或其他聊天模型，然后不停地提问。这样虽然方便，但每次都需要等待模型生成一段回答。一来一回会消耗时间，也会消耗较多 token。更重要的是，我们最后看到的是模型重新组织过的文字，还要回到论文里确认它对应的原文在哪里。

所以我真正需要的并不是另一个论文总结工具。我需要的是：

> 我提出一个问题，系统立即把最相关的原文找出来，然后由我自己阅读和判断。

PaperFocus 做的就是这件事。

## 为什么使用 Jev

传统的大语言模型主要擅长生成内容。我们给它一个问题，它会逐个 token 地生成一段回答。

Jev 的工作方式不同。它接收一份文本和一些明确的问题，然后直接返回结构化的判断、分数和概率。官方目前提供三种基本判断方式：

- **Choice**：从多个选项中选择一个；
- **Score**：按照给定标准进行评分；
- **Noul**：判断一个陈述成立的程度。

这些问题可以在一次请求中并行完成。Jev 不生成解释、代码或者长篇回复，而是返回软件可以直接使用的决定和概率。

PaperFocus 使用的主要就是评分能力。我先在本地解析 PDF，保留每个段落、句子和图注在页面上的位置。然后把用户的问题和候选文字交给 Jev，让它判断每一处内容与问题的相关程度。最后再由普通代码负责排序、筛选、定位和高亮。

整个流程可以概括为：

> **本地解析 PDF → Jev 判断相关性 → 代码把结果映射回原论文。**

所以 Jev 负责语义判断，代码负责界面、坐标和工作流程。

TypeSafe 将 Jev 的训练方法称为 **RLCD**，全称是 *Reinforcement Learning for Calibrated Decisions*，可以理解为“面向校准决策的强化学习”。

RLHF 更关注人类喜欢哪一个回答，RLVR 更关注答案能不能被验证，而 RLCD 更关注这个判断是什么，以及模型对这个判断到底有多确定。

不过，概率校准描述的是大量判断的总体规律，并不保证某一次回答一定正确。因此在重要场景里，最终仍然需要代码规则或者人工复核。

## 如何搭建

搭建过程其实非常简单。

第一步，进入 TypeSafe 的控制台注册账号并创建 API Key。

我注册时，账户里获得了 5 美元的试用额度。这个属于当时控制台提供的额度，具体金额还是以大家注册时的页面为准。

Jev 当前官方价格是每一百万输入 token 0.042 美元，输出 token 免费。因为它返回的是很短的结构化判断，不会生成大段文字，所以分类和筛选任务的调用成本非常低。

第二步，可以在官方 Quick Start 页面直接复制 API 调用示例。官方既支持直接发送 HTTP 请求，也提供 Python 和 JavaScript SDK。

第三步，如果不想自己从头写代码，也可以安装 TypeSafe 官方提供的 skill，然后告诉 Codex 或 Claude Code：

> 我希望做一个上传论文、输入问题、自动定位相关原文的网页工具，请使用 TypeSafe skill 帮我设计并接入 Jev。

这个 skill 的作用，是让编程智能体理解 Jev 的接口、问题类型和推荐架构。它本身不是模型，也不是应用运行时。

我这个项目真正运行时，仍然使用 API Key 直接调用 TypeSafe 的官方接口。skill 只是帮助我更快地完成开发。

整个工具大概经过两三轮主要对话，就搭出了可以运行的版本。后面更多时间其实花在交互细节上，例如 PDF 坐标、句子高亮、图片定位、相关度筛选以及结果排序。

## 其他适用场景

Jev 适合的任务通常有两个特征：

> **第一，需要快速反馈；第二，本质上是判断、分类、评分或路由。**

### 1. 信息流筛选

每刷到一条内容，系统立即判断它是否属于广告、争吵、加密货币或者用户不想看的主题，然后决定正常显示还是折叠。

### 2. 实时游戏控制

系统读取当前游戏状态，然后从左、右、跳跃、前进等有限动作中快速选择一个。它不需要写一篇游戏攻略，只需要立即决定下一步动作。

### 3. 浏览器或语音控制电脑

用户说出目标，语音先转成文字，程序再把当前页面状态整理成结构化文本。Jev 从点击、输入、滚动、返回等候选动作中快速选择下一步。

### 4. 高频业务分类

例如判断客服消息应该进入退款、技术支持还是销售部门，或者判断一张发票属于正常、欺诈还是需要人工复核。

### 5. 语义定位

就像 PaperFocus 一样，它不重新生成论文，而是对大量候选段落进行相关性判断，然后找出最值得用户查看的位置。

## 结尾

所以，我觉得 Jev 最有意思的地方，并不是它能不能取代 GPT。

GPT 适合生成、解释、规划和复杂推理；Jev 更适合嵌入软件中，快速完成大量、明确、结构化的判断。

PaperFocus 就是一个很小的例子。

它没有试图替我阅读论文，而是把一种快速判断能力放进了论文阅读流程中：

> 我提出问题，它帮我找到位置；真正的理解和判断，仍然由我完成。

这就是我做这个工具的原因。
